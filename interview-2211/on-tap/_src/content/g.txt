@q 177
@time about 90 seconds
@ans
**The problem:** many services need to send notifications – push, email, SMS. If each service calls providers directly, we get duplicate code, no retry, and when a provider is slow, the caller becomes slow too.

**The design:** services send a request to a **gateway**, then to an intake service. The intake service checks the tenant's quota and puts an event into **Kafka**. Sender services consume the events and call the providers. I used **gRPC** between internal services, **Redis** for rate limiting and caching, and **PostgreSQL** to store the results.

**Key trade-offs:**
- Kafka gives **durability and replay**, but it delivers **at least once**, so I made the consumers **idempotent** with a PostgreSQL upsert on a unique key. Duplicate messages are simply ignored.
- Messages that fail too many times go to a **dead letter queue**, so one bad message does not block the others.
- I used a **basic saga**: if sending fails permanently, the quota is given back.

**Result:** it is a personal project, so I don't have production traffic, but I tested failure cases like killing a consumer and confirmed there were **no lost and no duplicate** notifications.
@honest Khung **problem → architecture → trade-off → result**. Nói thật “personal project, no production traffic”. Xem câu 33–40 (trang A6) để trả lời các câu đào sâu bằng tiếng Việt trước.

@q 178
@time about 60 seconds
@ans
Imagine a **busy restaurant**. Waiters take orders from customers, but they don't cook. They put the order tickets on a **rail in the kitchen**. The cooks take tickets one by one and cook at their own speed.

A **message queue** is that rail. One part of the system leaves a message, and another part picks it up later.

**Why do we need it?**
- **The waiter doesn't wait for the cook.** The customer gets a quick answer: “Your order is received.”
- **During rush hour**, tickets pile up on the rail instead of being lost. The cooks catch up later.
- **If one cook is sick**, the tickets are still there. Another cook can take them.
- We can **add more cooks** when there are too many tickets.

So a message queue makes the system **faster for users, safer during peaks, and more reliable when something breaks**.
@honest Không dùng thuật ngữ (producer, consumer, broker). Ví dụ nhà hàng hoặc bưu điện đều được. Câu chốt tóm ba lợi ích.

@q 179
@time about 90 seconds
@ans
**Situation:** In our warehouse system, the robot station sometimes **rejected totes** because they were heavier than the 30 kg limit, but our system said they were fine.

**Task:** I owned the API that records items put into totes, so I had to find the cause.

**Action:** I checked the logs and saw that two stations had written to **the same tote within a few hundred milliseconds**. The code **read the weight, checked the limit, then wrote** – three separate steps. So both requests read 22 kg, both added 6 kg, and the tote became 34 kg. I **reproduced it** with an integration test: two threads started at the same moment on a real PostgreSQL database. Then I **combined the check and the write into one conditional update**. If no row was updated, the API returned a clear “tote overloaded” error.

**Result:** The test ran hundreds of times without failing, and the problem **did not happen again** in production. I learned to look for **check-then-act** patterns whenever I see shared data.
@honest STAR, **quá khứ đơn** xuyên suốt (*checked, saw, reproduced, combined*). Con số 22 + 6 + 6 = 34 làm câu chuyện dễ nhớ.

@q 180
@time about 60 seconds
@ans
A **database** is the **source of truth**. It stores data durably on disk, it supports transactions, and it is the place we trust.

A **cache** is a **fast copy** of some data, usually in memory, like Redis. We use it because reading from memory is much faster than querying the database, and it reduces load on the database.

**The main risk is stale data.** The database is updated, but the cache still has the old value, so users see wrong information. This happens because updating the database and the cache are **two separate steps**.

**How I handle it:** update the database first, **then delete the cache key**, so the next read loads fresh data. I always set a **TTL**, so even if something goes wrong, old data expires. And for data that must be exact, like money or stock, I read from the database, not the cache.

Other risks: if the cache goes down, all traffic hits the database at once, so we need protection like rate limits or circuit breakers.
@honest Ba ý: **DB = nguồn sự thật**, **cache = bản sao nhanh**, **rủi ro = dữ liệu cũ** + cách xử lý. “Stale” đọc /steɪl/.

@q 181
@time about 60 seconds
@ans
First, I **listen** and make sure I understand their idea and the reason behind it. Often they see a problem I didn't see.

Then I try to **move the discussion to data**, not opinions. We agree on criteria – for example correctness, performance, complexity and cost to operate – and compare both options. If possible, we do a **small test** or a quick benchmark.

For example, a teammate wanted to use a Redis lock to fix a race condition. I suggested a conditional update in PostgreSQL. We compared them: both were correct, but mine had no extra infrastructure and held the lock for only a few milliseconds. We also wrote down **when we would change the decision**.

If we still disagree, we ask the tech lead to decide. **Once the decision is made, I commit to it** and help make it work, even if it wasn't my idea.
@honest Cụm khóa: *listen → criteria/data → small test → escalate → disagree and commit*.

@q 183
@time about 60 seconds
@ans
I use **three layers of protection**.

**First, an idempotency key.** The client sends a unique key with each operation, for example in an `Idempotency-Key` header. When it retries, it sends **the same key**.

**Second, a unique constraint in the database.** The server stores the key with a unique constraint and saves the result. If the same key comes again, the server **returns the saved result instead of doing the work again**. I don't rely on “check first, then insert”, because two requests can pass the check at the same time.

**Third, the client retries correctly:** only for errors that are safe to retry, like timeouts or 503, not for 400 errors; with **exponential backoff and jitter**, so many clients don't retry at the same moment; and with a limit on the number of retries.

In my Notification Hub, consumers are idempotent with a PostgreSQL upsert, so even if Kafka delivers a message twice, the user gets **only one notification**.

@q 184
@time about 90 seconds
@ans
I would go **step by step, from the big picture to the detail**.

**Step one, metrics.** When did it start? Is it all endpoints or only one? Did it start right after a deployment? I look at **p99 latency, error rate, and saturation** like CPU, memory and the database connection pool. If it started after a deploy, I would **roll back first** to protect users.

**Step two, traces.** I open a few slow requests in the tracing tool, like Datadog APM, and see **where the time goes**: the database, another service, or our own code.

**Step three, slow queries.** If it's the database, I find the query and run **EXPLAIN ANALYZE**. Usually I see a missing index, a bad join, or an N+1 problem.

**Step four, thread dumps.** If CPU is low but requests are slow, threads are probably **waiting** – for a lock or for a database connection. I take a few thread dumps with jstack and look for blocked threads.

Then I fix the root cause, **measure again** to confirm, and add an alert or a test so it doesn't happen again.
@honest Thứ tự **metrics → traces → slow query → thread dump → fix → measure**. Dùng *Step one, step two…* để người nghe theo kịp.
